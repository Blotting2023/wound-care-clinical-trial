## 二、V1 必做清单（黑线，缺了监管一票否决）

> 排期口径：从现在起 4~6 周，每项都有可演示的产物。**这一层落地之后才能找临床试验机构做 UAT**。

### A1. 受试者鉴认代码（去标识化）

- **数据模型**：`Patient` 加 `subjectCode`（拼音首字母 + 4 位顺序号，如 `ZW0001`），`displayName`（仅 UI 显示，可从 `subjectCode + 末四位电话` 派生）
- **真名映射表**：新表 `patient_identity_map`（`subjectCode → 真实姓名 + 身份证 + 电话`）**加密存储**（AES-256），App 端不直连
- **业务影响**：评估 / 报告 / 统计全部用 `subjectCode`；**不**再向 App 下发真实姓名
- **迁移**：现有 demo 患者补 `subjectCode`；CRF 历史数据批量改写
- **工作量**：3 天

### A2. 试验器械追溯

- **数据模型**：新增 `InvestigationalDevice`（`id, name, model, spec, lotNo, serialNo, receivedAt, protocolId, expiryDate, status`）
- **评估记录关联**：`Assessment` 加 `deviceId`
- **使用台账**：`DeviceUsageLog`（`deviceId, subjectCode, usedAt, operator, status, returnedAt, disposalMethod`）
- **UI**：患者详情页加"试验器械"标签 + 器械列表；新增评估时选器械
- **工作量**：5 天

### A3. 试验方案关联

- **数据模型**：新增 `Protocol`（`id, name, version, sponsor, piName, ethicsNo, startDate, endDate, status`）
- **关联**：每个 `Patient.subjectCode` 在入组时绑一个 `Protocol.id`（同一受试者只参加一个方案）
- **CRF 模板版本化**：`Protocol` 关联 `crfTemplateVersion`（v1 0.1.0 / v1 0.2.0 演进留痕）
- **UI**：新增"方案管理"页（创建 / 启停 / 版本发布）+ 评估页头部显示 `协议编号 v 版本号`
- **工作量**：4 天

### A4. 数据修改审计日志

- **数据模型**：`AuditLog`（`id, tableName, recordId, opType[CREATE/UPDATE/DELETE/SIGN], fieldName, before, after, reason, operatorId, operatorName, operatorIp, deviceId, appVersion, occurredAt`）
- **落地方式**：
  - 后端统一拦截：在 `DemoBackend`（或真实后端的 ORM 钩子）封装 `update()` / `delete()`，自动写 AuditLog
  - 客户端不可绕开：禁止直接 UPDATE / DELETE 业务表，只能通过 Provider 调 service → 调 backend
  - **审计日志只允许 INSERT，不允许 UPDATE / DELETE**（数据库层面 revoke 权限）
- **UI**：每个详情页（评估 / 创面 / 患者）右上角加"操作历史"图标 → 弹时间线
- **工作量**：6 天（含演示页 + 跨表）

### A5. 创面照片作为"影像源数据"

- **原始保留**：禁止压缩；上传到对象存储用 `multipart/original` 路径
- **元数据存档**：EXIF（拍摄时间 + 设备 + 焦距 + ISO + GPS）+ 校准卡识别结果 + 拍摄者 + 设备指纹
- **时间一致性**：拍摄瞬间 NTP 校时（取服务器时间做权威时间戳，设备时间仅作 EXIF 参考）
- **存储策略**：原始 + 缩略图两份；缩略图只是 UI 渲染用
- **导出**：详情页可"下载原始"，生成 zip 含 jpg + JSON 元数据
- **工作量**：4 天

### A6. 评估表与 CRF 范本对齐

- **现状映射**：现有评估表（创面 + 拍照 + NRS + VSS + 签名）→ 国家局 2016 CRF 范本
- **新增字段**：
  - **受试者鉴认代码**（A1 输出）
  - **试验方案编号 + 版本**（A3 输出）
  - **试验器械编号**（A2 输出）
  - **入组 / 访视日期**（按方案 visit schedule）
  - **伴随疾病 / 合并用药 / 合并用械**（CRF 范本第五项）
  - **AE 表**（V1 先做占位 + 必填校验，不做完整 SAE 流程）
  - **CRF 完成声明**（研究者最后签名 + 日期）
- **缺失数据约定**：每个字段定义 `ND / UN / NA` 三态
- **填写指南**：每字段鼠标 hover 提示（在 mobile 上改成 help 图标）
- **工作量**：5 天

### A7. 数据留存期管理

- **存储**：评估 / 照片 / 审计 / 签名永久保留（≥10 年）
- **数据库层**：业务表加 `archiveStatus`（active / archived / pending_destroy）；查询默认只看 active
- **备份**：每日增量 + 每周全量；本地 + 异地（V1 至少 S3 跨区复制）
- **介质迁移**：每 5 年评估存储介质 / 格式是否仍可读
- **销毁 SOP**：留存期届满 + 经 PI / 机构办审批后销毁；销毁记录归档 ≥5 年
- **工作量**：3 天（V1 简化版，留 SOP 文档）

### A8. 知情同意电子化（最小可用版）

- **V1 范围**：
  - 知情同意书 PDF 上传 + 版本号
  - 受试者手写签名（手机屏 / 签字板）
  - 签名时间 + 设备指纹 + IP
  - 留 PDF 副本给受试者（下载 / 推送）
  - 撤回 / 重新签署流程
- **不做的**：受试者人脸识别 / 视频见证 / 多语种
- **工作量**：6 天

### A9. PIPL 本地化存储

- **目标**：所有医疗数据 + 照片 + 审计落中国大陆对象存储（阿里云 OSS / 腾讯云 COS）
- **跨境通道**：禁止；后端 API 全部走境内 ECS
- **加密**：对象存储 SSE-KMS + 客户端 AES-256
- **密钥管理**：腾讯云 KMS / 阿里云 KMS
- **工作量**：4 天（V1 简化版只做存储层 + 加密，应用层加密延后）

### A10. 真实姓名不再下发给 App

- **App 端**：所有 UI 列表 / 详情 / 报告 / 拍照浮水印**只显示鉴认代码**（如 `受试者 ZW0001 · 男 · 56 岁`）
- **后端 API**：返回的 `Patient` 不带 `name`，只带 `subjectCode + gender + age + birthYearMonth`
- **导出**（统计 / 申办者报告）：永远不用真实姓名
- **工作量**：2 天

## 三、V2 建议清单（黄线，上线前 3 个月内完成）

### B1. AE / SAE 报告流程

- **数据模型**：`AdverseEvent`（`id, assessmentId, subjectCode, term, meddraCode, onsetAt, resolvedAt, severity[轻/中/重], relationship[肯定/很可能/可能/可能无关/无关], outcome[消失/继续/后遗症/死亡], actionTaken, isSerious`）
- **SLA 计时器**：本地 + 后端跑 24h / 7d / 15d 计时；到时未完成自动告警
- **报表**：申办者季度汇总 PDF（按 MedDRA 系统器官分类）
- **工作量**：8 天

### B2. 二次鉴别电子签名

- **现状**：单纯 UI 手写签名
- **升级**：签名时强制**短信 OTP / Touch ID / Face ID** 二选一
- **签名含义声明**：「我已审核并确认本评估与源数据一致」固定文案
- **不可分离**：签名图像 + 时间戳 + 设备指纹 + IP 写入 PDF 元数据
- **审计**：每次签名作为 AuditLog 的 SIGN opType
- **工作量**：5 天

### B3. 方案偏离记录

- **数据模型**：`ProtocolDeviation`（`id, protocolId, subjectCode, assessmentId, type[入排/用械/访视/知情/其他], description, severity, reportedAt, reportedBy, ethicsReportedAt`）
- **UI**：研究者每次发现偏离能"一键上报"；偏离累计到 ≥3 次自动标黄提醒
- **季度汇总**：申办者 + 机构办报表
- **工作量**：4 天

### B4. 数据导出（PDF + CDISC）

- **PDF**：每位受试者按方案产出完整 CRF 报告（含签名 + 审计摘要 + EXIF 概要）
- **CDISC SDTM**：导出 `DM / AE / EX / SV / VS / CM` domain（V1 先做 DM + EX + VS demo）
- **导出限速**：每人 1000 条 / 小时（防误操作）
- **审批**：导出超 100 条需 PI 二次授权
- **工作量**：10 天

### B5. 角色 × 操作权限矩阵

- **角色**：PI / Sub-Investigator / CRC / 监查员 / 申办者 / 数据管理员 / 伦理委员会
- **权限**：每角色 × 资源 × 操作（CRUD + 签名 + 导出 + 锁定）三维矩阵
- **实现**：JWT token + 角色 claim；后端 RBAC 中间件；App 端按角色隐藏菜单
- **delegation log**：PI 授权 CRC 做什么 → 写入数据库 + PDF 留档
- **工作量**：6 天

### B6. 数据库锁定（freeze）

- **场景**：方案结束 / 中期分析前 → 数据冻结
- **数据模型**：`DatabaseLock`（`protocolId, lockedAt, lockedBy, reason, unlockedRecords[]`）
- **UI**：PI / DM 可一键锁定；锁定后所有修改被拒，只能 unlock
- **审计**：锁定 / 解锁操作作为 AuditLog 顶层 opType
- **工作量**：4 天

### B7. NTP 校时 + 设备时间偏差告警

- **服务端**：NTP 时间作为权威时间戳写入每条记录
- **客户端**：拍照时若设备时间与服务器时间偏差 >5 分钟，弹警告 + 要求校正
- **存储**：`serverTime + clientTime + timeDiffMs` 三字段并存
- **工作量**：2 天

### B8. 异地备份

- **策略**：每日凌晨 3 点全量 + 6 小时增量 → 异地 OSS / COS 跨区复制
- **演练**：每月随机抽 1 份恢复验证
- **告警**：备份失败 / 恢复演练失败 → 飞书 / 钉钉群告警
- **工作量**：3 天

### B9. 必备文件上传与管理

- **类型**：伦理批件 / 方案签字版 / CRF 模板 / 知情同意书模板 / 研究者手册 / 保险单 / 监查报告
- **流程**：上传 → 自动 OCR 提取关键字段（方案编号 / 伦理批件号 / 有效期）→ 自动归档 → 自动到期提醒（伦理批件 1 年 / 保险单到期前 30 天）
- **版本管理**：每次修订留旧版本；旧版本只读
- **工作量**：6 天

### B10. 数据脱敏（统计 / 报告）

- **场景**：导出申办者 / 申办方报告时，**移除**真实姓名 / 身份证 / 电话 / 详细地址
- **保留**：鉴认代码 + 性别 + 年龄段（10 岁一档）+ 地区（到省）
- **导出审计**：每次导出写 AuditLog，PI 可见
- **工作量**：2 天

## 六、几个决策点（等你拍板）

1. **A3 试验方案关联**的颗粒度：是按"方案 → 多个版本 → 多个患者入组"（轻）还是"方案 → 多个中心 → 多个患者"（重，含中心配置）？建议 V1 走前者，V2 加中心。
2. **A8 eConsent**：先做**简化版**（PDF + 手写签名 + 设备指纹）还是直接上**完整版**（含视频见证 / 多语种 / 人脸识别）？完整版工作量大 3 倍。
3. **A4 审计日志**：客户端**只读**，还是给研究者一个"撤销操作"能力？GCP 倾向于**不可撤销**（错了就追加反操作），建议 V1 不可撤销。
4. **A9 PIPL**：存储用**阿里云 OSS** 还是**腾讯云 COS**？看你院 IT 偏好。两者都支持 SSE-KMS。
5. **B5 权限矩阵**：V1 阶段角色只有 2 个（PI / CRC）够不够？是否需要现在就预留 6 个角色？
6. **B4 导出**：先做 PDF 还是直接做 CDISC？CDISC 复杂度高 5 倍。

## 七、风险与对老胡的提醒

- **A1 真名脱敏**对患者列表 UI 有冲击 — 你需要决定**是否给 CRC 看真实姓名**（GCP 倾向不让看，PI 紧急时按权限可见）。如果完全不让看，建档录入要更严谨（错一个字后期难改）。
- **A4 审计日志**会**让数据库体积膨胀 30%~50%**（每改一次字段多一条记录）。V1 阶段评估量小没事，到 1000+ 评估需要做归档策略。
- **A8 知情同意**走电子化前需要先和**贵院伦理委员会**确认他们接不接受 eConsent；不接受的话 V1 仍要保留打印签字 + 拍照存档。
- **A9 PIPL** 选云厂商时还要查它**是否有医疗数据合规认证**（阿里云有"医疗云"、腾讯云有"医疗专区"）。
- **V1 必做清单总工作量约 42 工作日**（≈ 8 周单人），如果让 1 个 Flutter 工程师 + 1 个后端 + 0.5 个合规顾问并行做，可以压到 4~5 周。

## 八、2026-09-03 决策记录（老胡拍板）

| 决策点 | 锁定方向 | 落地含义 |
|--------|---------|---------|
| 1. A3 试验方案颗粒度 | **重：方案 → 多中心 → 多患者** | `Protocol` + `Center` + `ProtocolCenterAllocation` 三级；入组记录直接绑 `protocolCenterId`；需多建 1 张表，多写 1 个 UI（中心列表 / 中心创建） |
| 2. A8 eConsent 范围 | **简化版：PDF + 手写签名** | 不做视频见证 / 多语种 / 人脸识别；签名页 = 加载 ICF PDF + 签名画板 + 设备指纹 + 时间戳 |
| 3. A4 审计日志 | **只读 / 不可撤销** | AuditLog 表只给 INSERT 权限；不提供"撤销"API；错了只能由 PI 写一条"反操作"记录 |
| 4. A9 PIPL 云厂商 | **腾讯云 COS** | 配合 SSE-KMS；密钥走腾讯云 KMS；首次需开通 COS Bucket（地域选广州/上海医疗合规节点）+ KMS 实例 |
| 5. B5 角色矩阵 | **预留 6 个角色** | `PI / SubI / CRC / Sponsor / IRB / Admin`（V1 实际只用前 2 个，但数据模型 + 权限枚举 6 个全占位，避免 V2 改表） |

### 决策影响下的 V1 工作量调整
